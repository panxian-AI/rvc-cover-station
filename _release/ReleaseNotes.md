# RVC 翻唱站 v2.1.3 · 更新包加校验（功能同 v2.1.2）

> **这一版不修你能看见的 bug，修的是一个「看不见但很要命」的洞。**
>
> 控制台的「立即更新」会从 GitHub 和 7 个第三方加速镜像里挑最快的一条下载，
> 而之前只校验「是不是 zip、CRC 对不对」——这两项对**被人替换过的包**全都天然通过
> （篡改过的 zip 自己就带着算得过的 CRC）。也就是说：谁控制了一个镜像、且它够快，
> 就能给所有已装机器下发任意代码。
>
> 现在下载完会逐字节核对 SHA-256，期望值写在 Release 正文里（走 api.github.com，
> HTTPS，镜像改不了）。对不上就换线路，所有线路都对不上就**拒绝安装**。
>
> 功能与 v2.1.2 完全一致。已经在用的机器建议更新——不是因为多了功能，
> 是因为装完之后你的「立即更新」按钮才第一次是可验证的。

---

## 一、洞在哪里

**症状**：没有症状。这正是它麻烦的地方——被换过的包装进去，界面一切正常。

**真因**：`updater._download()` 的线路列表是

```python
urls = ["https://codeload.github.com/...",          # 官方
        "https://ghfast.top/https://codeload...",    # 以下全是第三方加速
        "https://ghproxy.net/...", "https://gh.llkk.cc/...", ...]
```

然后用 `speed.rank()` **按实测速度排序，最快的先下**。这个设计本身是对的（不排序的话
用户要等 60 秒超时才换线），但它意味着「谁快听谁的」。而当时的校验只有三条：
体积 > 1024 字节、开头是 `PK`、`zipfile.testzip()` 通过。前两条随便一个文件都能过，
第三条是 CRC——**CRC 是包自己带的，改了内容重新打包，CRC 仍然对**。

所以这条链上唯一可信的东西是「我从官方下到的字节」，而代码从来没确认过这件事。

## 二、怎么修的

**期望值放哪**：Release 正文。客户端本来就要请求 `api.github.com` 拿版本号和更新说明
（HTTPS，证书校验由 urllib 负责），正文跟 Release 一起创建，改它需要仓库写权限。
发布脚本现在会在上传完资产之后，把**客户端真正下载的那个包**（tag 源码 zip）的
SHA-256 算出来写进正文：

```
**在线更新用的 tag 源码包**（控制台点「立即更新」下载的就是这个）
update_zip_sha256: `9f2c…（64 位）`
```

**客户端怎么用**：`_download()` 每条线路下完先过 CRC，再过哈希；不一致就记下原因换下一条，
界面上能看到每条线路的死因。全是「校验失败」时直接抛：

> 所有线路给出的更新包都与发布页公布的 SHA-256 对不上，已拒绝安装。
> 这通常意味着某个加速镜像返回了被替换的内容；请到 Release 页面手动下载完整安装包安装。

**没有校验值怎么办**：**拒绝自动更新**（fail closed），按钮变成「需手动下载安装包」，
并指向 Release 页面。以前「拿不到期望值就照装」等于把洞留着——攻击者只要让正文里那个
值读不到就行。真想跳过（比如自己改了镜像做测试）才设 `RVC_ALLOW_UNVERIFIED_UPDATE=1`。

**落盘前还有一道**：`_apply_locked()` 在解压覆盖之前再核一次。`_download()` 已经验过了，
这一层是为了「以后有人重构下载逻辑、把校验弄丢了」也不至于直接写坏盘——解压是会覆盖
用户代码文件的。

## 三、发布脚本也一起改了

以前「公布校验值」要靠人记得。现在 `create_release.py` 上传完资产接着做四件事，任何一步
不对就退出、不留下半套：

1. 核对上传后的资产 digest 与本地文件一致（GitHub 会回 `sha256:` 摘要）；
2. 下载 tag 源码包，算 SHA-256；
3. **再下一次、再算一次**——两次不一致说明 codeload 对这个 tag 不稳定，写进正文会让
   所有已装机器拒装，所以宁可这次不发；
4. 写进正文后回读一遍，确认客户端真能取到那个值。

## 四、说清楚这一版还没解决的

- **这不是数字签名。** 它防的是「镜像换包」，防不了「仓库被入侵」——正文和包都出自
  同一个账号。要做签名得引入一对密钥，客户端内置公钥，那是另一个量级的改动。
- **已经装了 v2.1.2 及更早版本的机器，这一次更新本身仍然是不校验的**——因为校验逻辑
  就在新包里。这是这类「自举」问题的固有次序：装完 v2.1.3 之后，往后的每次更新才受保护。
- 更新包大小上限、解压清单、失败回滚这些原有保护没变。

## 五、更新方式

1. 控制台右上角提示有新版本 → 点「立即更新」。这一版会显示「安装前会逐字节核对 SHA-256」，
   装完的提示里也会带上核对过的哈希前 16 位。
2. 更新完重开 `启动RVC.bat`（`updater.py` 是启动时加载的）。
3. 也可以直接下新版一键安装包覆盖安装，个人数据会保留。

## 六、测试

`e2e_update` 从 47 项扩到 **66 项**，新增的 19 项都在这条链上：

- 正文里 5 种写法都能取到校验值（裸行 / 代码块 / 大写 / 中文标签 / 带空格换行），
  以及「别的哈希不会被误当更新包哈希」；
- 一致放行、不一致给中文原因、没有期望值绝不放行；
- **造一个结构合法、CRC 也算得过的被换包**，断言它被拒（这条最容易测错：直接改字节会
  先被 CRC 拦下，那样测到的根本不是哈希这条路）；
- 一条线路被换包时自动换下一条；
- 没公布校验值时 `apply()` 直接拒绝，`RVC_ALLOW_UNVERIFIED_UPDATE=1` 才放行；
- 即使把 `_download` 换成不校验的桩，落盘前那道也会拦住，且**一个文件都没写**。

全套 **19 套 1028 项**，全绿。
