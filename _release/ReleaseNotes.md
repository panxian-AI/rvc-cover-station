# RVC 翻唱站 v2.1.4 · WebUI 单实例与显存修复

> **症状**：昨天还好好的，今天一推理就失败，报错写着
> `AttributeError: 'NoneType' object has no attribute 'dtype'`，
> 常见原因让你「重跑一键安装.bat」——重装了也没用，过几天又犯。
>
> 这一版把这条误导链整个拆掉：真正的故障原因一直被两层包装盖着，
> 用户看到的、日志里抓到的，全都是最外层那个没有诊断价值的假错误。

---

## 一、真因：报错是三层套娃，最外层全是误导

**第一层（真因）：显存被多个 WebUI 实例分掉了。**

WebUI 以前的逻辑是「端口被占就自动换下一个端口继续启动」。听起来贴心，
实际上后端把 WebUI 地址写死成 `127.0.0.1:7865`——被挤到 7866 的实例
**没有任何程序会去用它**，唯一的副作用是：它照样把 hubert、rmvpe、声线
模型各装一份进显存。

叠到第三份就是 CUDA out of memory。而且显存一爆，那个进程的 CUDA 上下文
就**彻底报废**，之后所有推理只会报 `CUDA error: unknown error`，
只能重启进程。用户体感就是「昨天还好好的，今天全废了」。

实测一台出故障的机器：**三个 WebUI 进程同时活着**，只有一个还在监听、
而且监听的是 7866 不是 7865；另外两个连端口都不监听了，却各自占着
500MB 内存和一份显存——僵尸。

**第二层（症状被吞）：推理失败时返回了 None。**

WebUI 内部 `vc_single()` 推理失败时把 `(None, None)` 当音频交回给 gradio。
gradio 的 Audio 组件后处理会去读 `data.dtype`——读 None 当然炸。
于是页面上、日志里，你看到的永远是
`AttributeError: 'NoneType' object has no attribute 'dtype'`，
真正的 `CUDA out of memory` 被埋在上面几十行。

**第三层（归因错误）：后端只取日志最后一条报错。**

`_webui_tail_error()` 从 WebUI 日志尾部抓最后一条 `XxxError`——
抓到的恰好是第二层那个 dtype 假错误。于是「常见原因」猜的全是错的，
把用户引去重装环境、换模型、重跑安装器，没有一条对症。

## 二、怎么修的

**1. 同一个端口只允许一个 WebUI（`webui.py`）**

- 进程一启动（还没加载 torch）就探测端口：已经有 WebUI 在服务，直接退出
  并说明原因，**几毫秒结束**，不会先花一分半加载模型再退。
- 端口被占不再自动换端口：被挤到 7866 的实例后端连不上，纯属白占显存。
  确实要并行多开（压测）时设 `RVC_WEBUI_ALLOW_MULTI=1`。
- 守卫的位置有讲究：放在 `import torch` 之前（有回归断言守住），
  晚了模型已经进显存，守卫就白做了。

**2. 面板自动清理重复实例（`panelkit/services.py`）**

点「启动」之前，面板会扫描 7865~7880 端口段 + 所有命令行含 `webui.py`
的进程，把多余的真身全部杀掉、只留一个干净的；「停止」也按同一段扫全，
以前只按 7865 找，杀不到飘到 7866 的孤儿。

- 健康形态 = 恰好一个真身（venv 的 pythonw 是转手壳，不算）且在 7865。
  多一个真身就触发清理——因为没法判断哪个实例的 CUDA 上下文还是好的，
  留着坏的反而继续占显存。
- 为什么扫命令行：实测有两个僵尸**不监听任何端口**，只按端口永远找不到
  它。psutil 没装、wmic 在 Win11 24H2 已移除，这里用
  `NtQueryInformationProcess` 直接读（不新增依赖）。

**3. 推理失败不再返回 None（`infer/vc/modules.py`）**

失败时给一段 1 采样的静音，把完整报错放进状态文本。前端显示的是真因，
不再是 dtype 假错误。

**4. 报错按真因给建议（`app_rvc.py`）**

归因函数先跳过「症状行」，优先抓 CUDA/显存类报错；建议也分派：

- 显存/CUDA → 明确告诉你「这是显卡问题，重装没用」，给重启步骤；
- 模型加载不匹配 → 这才建议重跑一键安装；
- 文件缺失 → 指向声线文件；
- 其它 → 原来的通用清单（顺序也调对了：显存问题排第一）。

**5. 双击启动后，右下角有一张「正在启动」的小卡片（`launch_silent.py`）**

以前黑窗一闪就没了，浏览器要等十几秒才开——这段空窗期里用户分不清
「在启动」还是「没反应」，于是又双击一次，正好叠出第二个 WebUI
（这就是上面三个实例的来源）。

现在双击后右下角立刻出现一张卡片：「正在启动面板…（已等待 N 秒）」，
就绪后变「已启动，正在打开浏览器…」然后自动关闭；失败时卡片收掉、
弹窗说明原因。tkinter 不可用时自动降级，绝不会因为提示窗起不来
把启动搞挂。

## 三、老用户怎么办

1. 控制台点「立即更新」，更新完**重开 `启动RVC.bat`**。
2. 第一次启动时面板会自动清掉已经叠出来的多余 WebUI 进程，
   提示里会写「已清理 N 个重复/错位的 WebUI 实例（端口 …）」——
   看到这句说明之前的卡顿/OOM 根因已经清掉了。
3. 以后双击启动，右下角会先出现「正在启动」卡片；**没看到卡片才是没启动**。
4. 如果再遇到推理失败，报错会直接告诉你是显存、文件还是模型的问题，
   按提示处理即可；只有模型加载不匹配才需要重跑一键安装。

## 四、说清楚这一版还没解决的

- 已经处于「CUDA 上下文报废」状态的进程，仍然只能靠重启恢复——
  现在的改进是：报错会明确告诉你该重启，而不是让你去重装。
- WebUI 本体（infer/ 目录）来自上游 RVC 项目，这次的修改以补丁形式
  维护在仓库里；将来升级上游时需要留意 `guard_single_instance` 和
  `vc_single` 这两处（回归断言会在被覆盖丢失时报警）。

## 五、更新方式

1. 控制台右上角提示有新版本 → 点「立即更新」。
2. 更新完**重开 `启动RVC.bat`**（这次改了 WebUI 和后端，重启才会生效）。
3. 也可以直接下新版一键安装包覆盖安装，个人数据会保留。

## 六、测试

全套 **19 套 1046 项**，全绿。新增断言：

- `e2e_silent` 新增 E 段 11 项：Splash 卡片存在、等待循环有状态更新、
  每个模态弹框前先收卡片、**守卫必须在 import torch 之前**、
  多开放行开关、换端口默认关闭、推理失败不再返回 None 音频、
  归因跳过症状行、CUDA 有专属建议、**用假日志实测抓到真因**；
- `e2e_stop` 新增第 8 段 7 项：端口线索找到实例、单个真身判定健康不动、
  两个真身触发清理、提示带端口、清理后端口释放、进程真的死了。
